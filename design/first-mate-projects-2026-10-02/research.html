Projects can make First Mate much easier to start. The session lifecycle already supports the prompt handoff. The new work is saving locations and browsing folders on each machine.

Research and design proposal. Application and server changes are not implemented.

The product recommendation

Make Use a project the default, with Manual setup beside it. A project stores one machine and one folder. iOS, web, or anything else can be part of its name without introducing a new project-type setting.

Creating a project from the form returns to the same draft, already selected. The starting prompt becomes the first message. Derive the initial session name from that prompt and allow renaming later.

Keep offline projects visible with their machine and last known path. Starting requires that machine to be available. Editing a project changes future sessions; existing sessions retain their original folder.

Each machine owns its projects

Store projects beside First Mate state on the companion that owns the folder. The Mac combines the project lists across its configured connections, following its existing fleet model.

Mac project picker
 Studio Mac companion  →  iOS App  →  local folder
 Laptop companion      →  Web App  →  local folder
 Build Server          →  offline, last known projects

The folder picker asks the selected companion to enumerate its own immediate directories over the existing authenticated connection. No new SSH credential distribution or central remote-command service is needed.

Use explicit server and connection identity. The saved Mac machine ID and the private configuration roster ID are different namespaces today. Never infer destination from display names, ordering, or a hostname fragment.

One request, one starting prompt

POST /api/v1/first-mate/features
{
  "title": "Investigate APP-204",
  "goal": "Read APP-204 and propose a plan.",
  "project_id": "project_example",
  "expected_project_revision": 1,
  "request_id": "request_example"
}

The server resolves the project, checks the folder, and creates the feature and first message together. It snapshots the project name, path, and revision so later edits never redirect existing work.

Check the original request receipt before re-resolving a project on retry. If a response was lost after creation succeeded, retrying must return the same feature even if the project has since changed. Keep the prompt intact and never enqueue it twice.

Folder picker behavior

  • Always show the selected machine, current path, parent navigation, and folder-only rows. Offer path entry and an explicit hidden-folder toggle.
  • Changing machines clears the chosen folder. Late results from a previous machine cannot update the new selection.
  • Show missing folders, permission denial, and offline machines as different states. Preserve the draft when something fails.
  • Browse only through authenticated companion access. Bound directory results; avoid recursive scans and file contents.
  • Resolve paths and symlinks on the destination. If private browse roots are configured, enforce their boundaries after resolution.

A small, staged implementation

  1. Server foundation: private project records, migrations, capabilities, directory listing, and focused filesystem/authentication tests.
  2. Creation contract: project-backed requests through the existing atomic feature/message path, preserving the legacy manual request.
  3. Mac experience: fleet project index, project editor, remote folder picker, then the new-session form.
  4. Compatibility and delivery: optional shared metadata, old-server fallback, native and API checks, and separately distributed matching companion packages.

The highest-value tests are wrong-host responses, offline destinations, inaccessible or moved folders, stale project revisions, and a lost response followed by a retry. Existing iOS and web clients should keep working with the manual contract.

The Mac update feed installs only the Mac app. Each participating companion needs the matching server package for project storage and folder browsing.
