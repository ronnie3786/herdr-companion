## Scope

**Phase 0, groundwork**
- `herdr_harness/watchers/schedule.py` with the four schedule kinds (`interval`, `daily`, `cron`, `once`), per-watcher IANA timezones through `zoneinfo`, a field-wise next-fire search (no minute scan), and a bounded "no next run" result. Port Cronboard's four tests as a seed, then write the real suite: Vixie semantics for `*/n` in the day fields (a field that starts with `*` counts as a star for the day-of-month/day-of-week rule), DST gap and overlap, month ends, 29 February, DOW 7, names, steps and ranges, `interval` with `days` and a half-open `window`, `once`, and the missed-run computation.
- The definition validator (hand-rolled; the package has no dependencies) covering all four step kinds, and the summary chip-markup validator with the rules in plan §4.2. Both with tests.
- Avatar SVG export is **deferred to the Phase 3 kickoff**; do not do it here.

**Phase 1, companion core, scripts only** (suggested order; commit at each checkpoint)
1. `watchers/store.py`: `watchers.sqlite3` with definitions and revisions, drafts, runs, step_runs, gate_state, inbox_items, deliveries, receipts. Follow `FirstMateStore` for pragmas, 0600 files, additive migrations and `request_id` receipts. Retention pruning (30 days or 200 runs per watcher, inbox 90 days) lives here and runs from an hourly sweep in Phase 1.
2. `watchers/runner.py` plus `steps/script.py`, `steps/gate.py` and inbox delivery: a detached worker spawned as `[sys.executable, "-P", "-m", "herdr_harness.watchers.runner", "--run", <run-dir>]` with `start_new_session=True`, holding `<run-dir>/runner.lock`, executing a frozen revision snapshot, heartbeating every 5 s.
3. `watchers/runtime.py`: the scheduler, a lazy `HerdrService.watchers` property started from `service.start()` only when enabled, guarded by `watchers/manager.lock`, with overlap `skip`, capacity, catch-up and reattach.
4. `/api/v1/watchers/*` routes, `WatchersError` mapped in `_dispatch`, the `watchers-v1` capability, SSE events, `docs/watchers.md` as the contract, a `release/notes/companion-next.md` entry, and a README "Optional integrations" row.

6. Agent-facing docs, so an agent can set watchers up unaided: a `herdr-docs watchers` topic and an `agent-docs/overview.md` entry that teach the draft, script, preview, dry-run flow, say that activation is the person's step, and point at `schema` and `example`.

**What the design reads, and the field Phase 1 must supply.** Return these from `GET /watchers` and `GET /watchers/{id}` now.

| In the design | From the server |
|---|---|
| Status word: On watch, Working now, Resting, One-time task, All done, "Draft, not scheduled yet" | `state` (`draft`, `active`, `paused`, `done`), `schedule.kind`, and `live` |
| Avatar, and its working, resting and "!" overlays | `avatar` (an id from the two lists: a character when any agent step exists, else an instrument), `live`, `state`, `attention` |
| Who line: "Sol with scripts on Desktop", "Script on Laptop" | `kind` (`agent`, `hybrid`, `script`; deliver steps do not count as scripts), the agent step's display name, `machine: {id, name}` |
| Summary with chips | `summary` markup, with `schedule.summary` filling `{time}` |
| "Next: in 8 min", and the next-to-wake pill | `next_fire_at` (ISO, UTC); clients format it and pick the soonest |
| "Step 2 of 4", the step label, the progress bar | `live: {run_id, step_index, step_count, step_id, step_title, started_at}` and `watchers.run` events; progress is steps done, never a timer |
| "My last run needs attention." | `attention: {reason}` when the last run is `failed` or `unknown`, or a delivery failed |
| Run now or Stop run, Pause or Wake up, Past runs with a count | `run_now`, stop, `pause`, `resume`; `runs_count` |
| Past runs: Finished, Nothing new, Needs attention, Stopped; when; duration; one sentence | run `status`, `started_at`, `duration_seconds`, and a plain-language `summary` the runner writes, such as "Nothing new. Stopped at the check." |
| Filters (All, On watch, Resting, Scripts only) and search | `state` and `kind`; search is client-side over name, summary text and machine |
| Builder's "How it runs" list | each step's `kind`, `title`, optional `note`, `icon` and `file`; script text from the scripts route |

- **The `{time}` phrase.** `schedule.summary` follows `cadence()`: lowercase, no closing period, for example "every 15 min", "every hour, weekdays 7 AM–10 PM", "weekdays at 7:00 AM", "every night at 1:00 AM", "today at 3:00 PM". Clients capitalize it at a sentence start. A `cron` schedule that fits none of these reads "on a custom schedule", with the raw expression returned beside it.
- **Chip grammar.** The nine tokens in plan §4.2, written `{kind}` or `{kind:value}`, with no nesting and no braces inside a value. The server stores the markup untouched; gluing trailing punctuation to a chip is the client's job.
- **Vocabulary.** Use the design's words in run summaries, CLI output and docs: watcher, on watch, resting, working, needs you, nothing new, wake up, past runs, Watcher inbox.
- **Ordering.** Working first, then needs you, then by next fire; resting and done watchers last. The server need not sort, but `GET /watchers` must carry what the sort reads.

## Contract details the plan left open (apply these)
- **Rollout.** Add `watchers` to the config allow-list and an `ENVIRONMENT_FIELDS["watchers"]` mapping to `HERDR_WATCHERS_*`, without requiring the section; `config.example.toml` documents it but notes that older companions reject the section. The feature is off unless `HERDR_WATCHERS_ENABLED=1`, read from the service's `environ` (as `response_audio.py` does), set under `[environment]` or `[machines.<id>.environment]`. Add `HERDR_HARNESS_WATCHERS_STORE_PATH` and `HERDR_HARNESS_WATCHERS_ROOT` to the derived state paths.
- **Disabled state.** `GET /watchers/capabilities` always answers: `{ok, enabled, capabilities, machine, timezone, steps, delivery, limits}` with `enabled:false` and empty `capabilities` when off. Every other watchers route returns 503 `watchers_disabled` naming the variable. `GET /api/v1` lists `watchers-v1` and the `watchers.*` SSE events only when enabled. The store and scheduler are not constructed when off.
- **Executable steps.** The schema accepts all four kinds, but this companion executes `script`, `gate` and `deliver` to `inbox` only; capabilities advertise `steps:["script","gate","deliver"]` and `delivery:{inbox:true,slack:false,notify:false}`. `activate`, `run_now` and `dry_run` refuse a definition with any other step (`step_kind_unsupported`). Drafts may hold such steps.
- **Activation.** `activate` requires `confirmed_by:"user"` and records `activated_by` and `activated_via`. Say plainly in docs and FINDINGS that agents hold the main token, so this is a convention and an audit trail, not a security boundary; a scoped token is future work. Keep `activate` out of the CLI's agent-facing verbs; a person runs `herdr-watchers activate ID --i-confirm`.
- **Scheduler.** Sleep until the next fire, capped at 30 s, and `wake()` on every mutation. Detect sleep and restart gaps from the wall clock since the last tick and apply `missed_runs` per watcher; `run_once` creates one `catch_up` run. Spawn failure marks the run `failed`. The scheduler, not the runner, publishes `watchers.updated`, `watchers.run` and `watchers.inbox`: poll the few `running` rows each tick and publish the diffs. `service.stop()` stops the thread and releases the lock but never kills runners.
- **Reattach.** The runner writes `finished_at` before releasing `runner.lock`. A `running` row whose lock is free becomes `unknown`, with a "needs you" inbox item, only when its heartbeat is older than three intervals.
- **Runner and scripts.** Script bodies are capped at 256 KiB. The step environment starts from `child_environment.agent_environment(environ, integration=False)`, drops every remaining `HERDR_*`, adds `HERDR_WATCHER_ID`, `HERDR_WATCHER_RUN_ID`, `HERDR_WATCHER_STEP_ID`, `HERDR_WATCHER_INPUT`, `HERDR_WATCHER_OUTPUT` and `HERDR_WATCHER_STATE_DIR`, and sets PATH from `HERDR_WATCHERS_PATH`, else a macOS default plus the companion's own `bin` directory from `sys.executable`. A step's result is its `HERDR_WATCHER_OUTPUT` file when written, otherwise its captured stdout. Use `pr_review_runtime._run_process_group` semantics: timeout kills the process group, 2 MiB output cap, full logs on disk under `watchers/<id>/runs/<run_id>/`. Both processes set `busy_timeout`, keep transactions short, and the runner opens the database only around writes.
- **Gate.** `new_items` and `changed`. The cursor is committed after the run's deliveries succeed, or at the end of a run with no deliver step, never on `dry_run`; cap it at the newest 5,000 keys. Prior art: `scripts/herdr_pr_review_watch.py`.
- **Runs without the app.** The scheduler and runners must work with no client connected; the Mac app is only a view. Capabilities and `GET /api/v1/health` carry `scheduler:{running,last_tick_at,next_fire_at}`. `herdr-watchers doctor` fails when the tick is stale, when the feature is off, or when the companion is not under a supervisor that restarts it (for example a bare tmux session), and says what to do.
- **Late fires.** When the gap since the last tick is shorter than the watcher's period, capped at 10 minutes, the missed fire runs once, late, as `scheduled`, regardless of `missed_runs`. `missed_runs` governs longer gaps. A companion restart must never drop a five-minute poll.
- **Timeouts.** Script steps default to 3,600 s and accept up to 21,600 s. Real jobs on the machine being replaced run for 30 minutes.
- **Hosts.** A watcher lives on exactly one machine, chosen at creation with `--machine` (default: the local companion). `machines` lists each roster machine with reachable, `watchers-v1`, enabled, supervised, timezone and executable steps. Ids are random and globally unique; fleet views key on machine plus id. A watcher created on another machine defaults to the creator's timezone. `export` writes a bundle of the definition and its scripts; `import --bundle` creates it paused on the target and never deletes the source. An unreachable machine fails with `machine_unreachable`.
- **Import from Cronboard: every job, in one step.** The decision is to migrate all jobs together, not one at a time. `import --cronboard-json FILE` reads the output of `cronboard list --all --json` (id, name, schedule, interpreter, command, enabled, scheduleTimeZone) and creates every job in one all-or-nothing call, idempotent by Cronboard job id. Each job becomes a one-step script watcher: a `cron` schedule in the job's timezone, the job body as the script, the same interpreter Cronboard used (`bash` is `/bin/bash`, `python` is `/usr/bin/python3`), the default timeout, an instrument avatar, `source: {kind: "cronboard", job_id}`, and a generated summary (`{time}, I run {script:<file>}.`). Disabled jobs arrive as drafts. Enabled jobs arrive **paused** when a person passes `--i-confirm`, which is recorded like an activation; without it they are drafts too. Use a synthetic ten-job fixture.
- **Import preview.** `--dry-run` creates nothing. It prints, per job, the watcher it would make and its next three fires beside Cronboard's own next run, so schedule parity is checked before anything changes, and it runs a preflight that executes nothing: interpreter present, schedule and timezone valid. **It never runs a job.** These scripts post their own results, so a watcher dry run of one is a real run.
- **Cutover and rollback, all at once.** `list`, `pause`, `resume`, `runs` and `inbox` accept `--source cronboard`. The cutover is: import with `--i-confirm`, disable every job in Cronboard, `resume --source cronboard`, then `doctor`. A resumed watcher schedules from now and never catches up. Rollback is `pause --source cronboard`, then re-enabling in Cronboard. The import prints both command lists, the exact `cronboard disable` and `cronboard enable` lines; it never runs them and never touches the crontab or Cronboard. After cutover, `runs --source cronboard --status failed,unknown` shows what needs attention. Write this procedure into `docs/watchers.md`.
- **Parity with cron's environment.** Scripts ran under cron with `HOME`, `LOGNAME`, `SHELL` and a minimal `PATH`, and received the body on stdin. The runner sets `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR` and `LANG`, and runs the body from a file. Imported bodies that export their own `HOME` and `PATH` keep working unchanged.
- **Runtime pruning.** `herdr-prune-runtimes` must skip a runtime that still has a live watcher runner.
- **Dry run.** Same runner, trigger `dry_run`; gate never commits; inbox delivery becomes a "would post" record attached to the run.
- **Schedules.** Machine timezone from the `/etc/localtime` symlink, then `TZ`, then UTC. `interval` fires align from local midnight (`every_minutes` 1..1440), filtered by `days` and `window`. Fixed-time schedules in a DST gap fire once at the first valid minute after it; in an overlap they fire once. A `once` watcher becomes `done` after its run.
- **Definitions and revisions.** The server stamps `machine` from its own id; a mismatching client value is rejected. Every change, including script content, increments `revision` (drafts too); runs pin a snapshot; `PATCH` takes `expected_revision` and recomputes `next_fire_at`; `DELETE` without `force` refuses an active watcher or a running run, and with `force` stops the run first. Add `GET /watchers/{id}/scripts/{step_id}` and CLI `script get` so a person can review what will run. Pick avatars server-side from the prototype's `CHARACTERS` and `INSTRUMENTS` id lists, copied into the package as constants (instruments for script-only).
- **API conventions.** Exact body keys, `request_id` replay with `idempotency_conflict`, `{ok:false,error:{code,message}}`, additive fields, 409 for revision conflicts (CLI exit 4), JSON on stdout and errors on stderr (exit 2), capability pre-check, `--machine` through `control_cli.machine_client`.
