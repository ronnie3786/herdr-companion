## A. What would have derailed the kickoff

1. **No starting point.** The main checkout at `~/projects/herdr-companion` is on `a52b20e`, **197 commits behind `origin/main`**, with 38 modified files of unrelated First Mate work and 15 untracked paths (**confirmed**, `git rev-list --left-right --count HEAD...origin/main`). `scripts/local-verify.py` and `scripts/verification_policy.py` do not exist at `a52b20e`; they do at `eac13aa`. An agent that starts where the prompt was written would build on stale code and could sweep up someone else's uncommitted edits. The prompt now requires a fresh worktree from `origin/main` and forbids touching the main checkout's working tree.
2. **The plan is untracked.** `design/watchers-2026-10-01/` and `design/watchers-prototype/` are untracked (**confirmed**, `git status`). A fresh worktree contains neither, so the old prompt's relative paths and its "write `FINDINGS-<date>.md` beside the plan" would point at nothing. The prompt now gives the absolute path and makes copying and committing the plan folder the first commit. `design/first-mate/` and `design/response-brief-2026-09-17/` are already tracked, so this follows precedent. The folder has no personal paths or tailnet names (**confirmed** by grep; `check-public-source.py` still runs).
3. **"Golden schedule tests ported from Cronboard" oversells.** Cronboard's `CronExpressionTests.swift` holds **four tests**: three summaries plus two parse errors, one weekday `nextDates` pair in UTC, one syntax match, and one `33 9 * * *` America/Chicago pair across the DST seasons (**confirmed**). That is a seed, not a suite. Worse, Cronboard's `isWildcard` is `raw == "*"` (`CronExpression.swift:197`), which is exactly the day-field bug the plan wants fixed, and its `nextDates` is a minute-by-minute scan up to 1,500 days. Porting its vectors verbatim would lock in the bug. The prompt now says: port the four as a seed, encode Vixie semantics for `*/n` day fields, and write the real suite (DST gap and overlap, month ends, Feb 29, DOW 7, names, steps, `interval` windows and days, `once`, bounded "no next run").
4. **Avatar SVG export does not belong in a companion kickoff.** The renderer is pure template strings behind `window.V2` (`v2-avatar-styles.js`, **confirmed**), so a Node export with a `window` shim is feasible. But it is Mac-facing asset work, needs Node and the untracked prototype, carries CSS-class animation hooks (`av-blink`, `av-bulb`) that must be stripped, and nothing in Phases 0–1 consumes it. It is deferred to the Phase 3 kickoff.
5. **Retention is contradicted inside the plan.** §12 Phase 1 verification lists retention tests and §13 says "Retention from Phase 1", while §12 Phase 5 lists "retention job". Resolved: Phase 1 ships store-level pruning on an hourly sweep; Phase 5 adds UI controls.
6. **Dry run was missing** from the old prompt's Phase 1 list although §12 Phase 1 includes it ("actions"). Restored, with Phase 1 semantics defined.
7. **No delivery boundary.** The old prompt said "report the delivered revision" but not whether to land, publish, or enable. `AGENTS.md` forbids inferring server cutover authority. The deliverable is now a pull request with Verify and "Mac tests (local)" green; landing, publishing the companion package, and enabling on any machine are separate explicit steps.

## C. Holes in the plan, and what the prompt now says

1. **Activation is a convention, not a boundary.** Agents receive the main token, so any agent can `POST .../actions {action:"activate", confirmed_by:"user"}`. The plan's "only a human click puts a watcher on watch" is enforced only by the Mac UI and by leaving `activate` out of agent discovery. The prompt says so plainly: keep the field, record `activated_by` and `activated_via` on the watcher, keep `activate` off the CLI's agent-facing verbs, and write the limitation into FINDINGS. A real boundary needs a scoped token that lacks `activate`; the server already has scope infrastructure (`_authorization_scope` with `active_work_*` scopes), but issuing agents a reduced token is a cross-cutting change that is out of scope here. **proposal**
2. **The runner cannot publish SSE.** It is a separate process with no broker and, by design, no API token. The scheduler thread must notice run and step changes (poll the few `running` rows each tick, cheap) and publish `watchers.run` itself.
3. **Disabled state was undefined.** Now: `GET /watchers/capabilities` always answers, with `enabled:false` and an empty `capabilities` list when off; every other watchers route returns 503 `watchers_disabled` naming the variable; `GET /api/v1` advertises `watchers-v1` only when enabled; the store and scheduler are not constructed when off.
4. **Step kinds the companion cannot run.** The schema knows all four kinds so later phases do not change the contract, but Phase 1 executes only `script`, `gate` and `deliver` to the inbox. Capabilities now advertise `steps` and `delivery`, and `activate`, `run_now` and `dry_run` refuse a definition with an unexecutable step (`step_kind_unsupported`). Drafts may hold such steps.
5. **No way to read a script back.** A human must be able to review what will run as the operator. Added `GET /watchers/{id}/scripts/{step_id}` and CLI `script get`.
6. **Machine timezone discovery** was unstated. `/etc/localtime` symlink target, then `TZ`, then UTC; per-watcher `timezone` validated with `zoneinfo.ZoneInfo`.
7. **DST and interval anchoring** were unstated. Fixed-time schedules in a skipped hour fire once at the first valid minute after the gap; in a repeated hour they fire once. `interval` fires are aligned from local midnight (`every_minutes` in 1..1440), filtered by `days` and a half-open `window`.
8. **A 1 s tick is churn without benefit.** The First Mate lag investigation showed what tight loops cost. Now: sleep until the next fire, capped at 30 s, woken by `wake()` on any mutation; sleep and restart gaps are detected by comparing wall clock to the last tick.
9. **Two processes write one SQLite file.** Both set `busy_timeout`, keep transactions short, and the runner opens the database only around writes, never across a script's execution. Status and heartbeat updates are single-row writes.
10. **Gate details.** The cursor is committed after the run's deliveries succeed, or at the end of a run with no deliver step; never on `dry_run`; capped at the newest 5,000 keys. A script's result is its `HERDR_WATCHER_OUTPUT` file when written, otherwise its captured stdout.
11. **Script environment.** Start from `child_environment.agent_environment(environ, integration=False)`, drop every remaining `HERDR_*`, add the watcher variables, and set an explicit PATH (`HERDR_WATCHERS_PATH`, else a macOS default plus the companion's own `bin` directory from `sys.executable`).
12. **`machine` in the definition** invites drift. The server stamps it from its own machine id on read; a client-sent value must match or is rejected.
13. **Reattach race.** The runner writes `finished_at` before releasing `runner.lock`. A `running` row whose lock is free becomes `unknown` only when its heartbeat is older than three intervals.
14. **Script size.** Script bodies are capped at 256 KiB per step at the API.
15. **Revisions.** Every definition change, including script content, increments `revision`, drafts included; runs pin a revision snapshot; `PATCH` on an active watcher recomputes `next_fire_at`; `DELETE` without `force` refuses an active watcher or one with a running run, and with `force` stops the run first.
