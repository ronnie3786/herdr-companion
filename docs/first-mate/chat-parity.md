# First Mate chat parity on Mac

The Mac app uses the same `PromptComposerView` for pane Chat and First Mate. First Mate supplies an explicit feature destination; it never creates a placeholder terminal pane or workspace.

## Behavior

- Return sends. Shift-, Option-, and Command-Return insert a newline while preserving native editing and undo behavior.
- **Attach**, drag and drop, upload status, retry, and remove use the selected feature's authenticated host. A failed or uploading selected file blocks sending until it is retried or removed. Attachment-only messages are valid.
- **Paste code** and Command-Shift-V append a fenced clipboard block.
- **Voice** — the microphone beside **+** starts click-to-stop dictation against the feature's host. An explicit **Stop** finishes the recording, waits for a nonempty transcript, appends it to the draft with the dictation marker, and submits the fully composed payload exactly once through the normal send path. A too-short, empty, cancelled, or failed transcription never sends an existing draft. A blocked or failed submit on a live destination keeps the transcript in the draft with an actionable explanation and no delayed automatic retry. Leaving the feature, backgrounding the app, reconnecting, or replacing the destination invalidates a pending auto-submit: a reconnect or a feature that no longer exists discards the late transcript with the obsolete lifecycle, while an invalidated but still-live original draft may receive it without a send or not-sent notice, and it is never sent to a new selection. **More → Record a voice note** opens the long-form recorder, whose record, preview, attach-raw-audio, and explicit Transcribe actions are unchanged and never submit. An automatic duration-limit completion also only appends; the recorder's own Stop and Transcribe controls keep their previous non-submitting behavior.
- Voice routing is opt-in per destination: First Mate swaps the microphone and the More voice entry, while pane Chat, the terminal composer, the HUD's unrelated local routing, issue reporting, iOS, and the web client keep their existing voice behavior. First Mate's send reuses the same permission, transcription provider/fallback, payload serialization, attachment readiness, destination validation, and request identity as a manual Send.
- Quotes use the shared quote editor, preview, chips, and inline `Quoted response segments:` serialization. Only the latest three completed text-bearing First Mate responses can be quoted; every visible human or assistant message remains copyable. Saving a quote only stages it.
- Draft text, uploads, quotes, and the dictation marker remain separate for each exact feature/connection lifecycle. Switching features or hosts cannot retarget an in-flight upload, transcription, send, catalog load, or settings save.
- First Mate reserves a local outgoing message synchronously on Return, Send, or dictation Stop. Its bubble says **Sending…** and comes before speculative working feedback, even in an empty lead chat; submitted text and staged item identities leave the composer before the POST suspends. The normal server row replaces the local presentation by receipt identity or a conservative one-to-one provisional display match. A refresh failure after accepted POST does not turn it into a send failure. Read markers and feedback use only server IDs. Pane Chat retains its acknowledgment-time cleanup.
- A rejected or transport-uncertain send stops speculative working, keeps a persistent red textual error (separate from refresh warnings), and retains the frozen text, quote, attachment, dictation marker, payload, lead context, and request identity. Transport uncertainty says delivery could not be confirmed, not that it was rejected. Failure restores the staged material only when the original composer has not been edited since detachment; otherwise **Copy failed message** and **Retry send** remain available without replacing newer edits. Retry is explicit and reuses the original payload and request ID; success never clears a newly typed identical draft. A feature or connection change cannot redirect a completion, and separate windows own separate drafts.
- Pane-only terminal keys, Pi maintenance, workspace file search, Jira insertion, skills, and conversation references are not offered for First Mate.

## Context and managed handoff

When the companion advertises `first-mate-context-v1`, the composer reports only the current native coordinator session's measured context tokens, window, percentage, handoff target, and observation time. Zero is a real measurement; missing, malformed, stale-session, or unavailable data is shown as unknown rather than zero.

At 90% of the configured target, the app distinguishes an approaching handoff from a reached threshold. Context details name the actual measurement time and explain the managed behavior: Second Mate checkpoints at a safe turn boundary and starts a fresh coordinator while retaining full history. Compaction is cancelled only inside managed sessions; ordinary Pi sessions keep their own compaction settings. There is no manual compact or handoff action in this interface.

## Safe model settings

Existing coordinator sessions require `first-mate-safe-model-settings-v1`. Selecting a genuine model or thinking change stages it and asks for explicit confirmation that context may be reprocessed, prompt caches may be invalidated, and additional cost may result. Workers are unaffected. The server applies the choice to the next coordinator turn without resetting the session.

Controls are unavailable while the coordinator owns a turn, a settings/send request is in flight, the feature is closed or offline, or the server cannot safely change an established session. The app submits the current settings revision and exact native session identity; stale or busy responses remain visible. Older servers remain usable for conversation and show an update affordance instead of attempting an unsafe mid-session fallback.

## Compatibility and setup

Optimistic presentation uses the existing authenticated First Mate POST and optional accepted-message receipt. Older companions that omit the receipt remain compatible; there is no new request field or server update for this Mac-only behavior. The standalone new-feature creation fallback on older servers is unchanged. Attachments require `first-mate-attachments-v1`; context telemetry requires `first-mate-context-v1`; safe established-session settings require `first-mate-safe-model-settings-v1`. These are companion-server capabilities. Updating the Mac app does not update or restart the server.

The upload request contains only `filename`, `content_type`, and `data_base64` and follows the shared 20 MiB attachment limit. The server owns storage under the feature's opaque namespace. Sent prompts reference returned attachment paths with the same ``Attachment: `path` `` convention as pane Chat.

Use synthetic features, files, messages, clocks, and model names. Do not capture operator configuration or real sessions.

- [ ] In light and dark appearance at every app text-size setting, long Markdown, code, quote chips, attachment errors, context status, and model labels remain readable.
- [ ] In both pane Chat and First Mate, verify multiline scrolling, undo/redo, Return to send, all modified-Return newline variants, Paste code, and Command-Shift-V.
- [ ] Attach by picker and drop; verify uploading, success, failure, retry, removal, attachment-only send, and that any failed selected file blocks send.
- [ ] Record a voice note; exercise hold, lock, finish, too-short, transcription success, and transcription failure.
- [ ] Click the First Mate microphone beside +, dictate a synthetic phrase, and click Stop once. Confirm exactly one transcribed message (including any staged text, files, and quotes) is submitted without another Send click, and that repeated Stop clicks, the primary Stop button, and the status-bar Stop all converge on that same single submission.
- [ ] Repeat the dictation Stop with an uploading or failed attachment, with control unavailable, and with a second submission in flight: confirm the transcript stays in its original draft with an explanation, nothing is sent, and no automatic retry occurs. Then repeat after switching features, backgrounding, closing the chat, reconnecting, and removing the feature mid-transcription: confirm the pending auto-submit is cancelled, an invalidated but still-live original draft may receive the transcript without the not-sent notice, and a reconnect or a gone feature discards the obsolete lifecycle's late transcript.

- [ ] Quote text and code from each of the latest three completed assistant messages. Confirm older and user messages copy but do not quote, Save does not send, and quote-only send serializes inline.
- [ ] Switch features and hosts while upload, transcription, send, catalog load, confirmation, and settings save are suspended. Confirm no completion mutates the new destination and every original draft survives.
